## 1. 本日概念与作用

### Schema Linking 不是字段名匹配

Schema Linking 把经营问题中的业务含义连接到可执行数据库结构。本项目至少包含五类连接：

1. 指标连接：如“GMV（不含运费）”连接到 `delivered_gmv` 及公式 `SUM(fact_order_items.price)`。
2. 时间连接：“2018 年 6 月”连接到指标默认时间 `fact_orders.order_purchase_timestamp`，并转成半开区间 `[2018-06-01, 2018-07-01)`。
3. 维度连接：“客户州”连接到稳定维度 `customer_state` 和字段 `dim_customers.customer_state`。
4. 过滤值连接：“已送达”连接到 `fact_orders.order_status = 'delivered'`。
5. 粒度与 JOIN 连接：订单、明细和支付粒度不同；同时使用明细与支付时，必须分别按 `order_id` 预聚合后连接。

字段命中只完成了其中一部分。`RetrievalDocument.fields` 仍是保守上下文，不是最小依赖或任意 JOIN 许可。

### Prompt 约束与程序校验分工

Prompt 告诉模型应使用哪些候选、输出什么 JSON、遵守哪些指标和粒度规则；它降低出错概率，但不能证明模型遵守了规则。因此流程仍保留三层程序边界：

- Pydantic 检查 JSON 结构、跨字段关系和时间范围；
- `MetricCatalog` 检查未知指标、未知维度及指标与维度兼容性；
- SQL 执行前检查单语句、只允许 `SELECT/WITH`、命名参数合同，并使用 SQLite 只读连接。

完整 SQL AST、表字段允许列表和查询超时属于 Day 8；根据数据库错误自动生成修复 SQL 属于 Day 9。

### 参数化查询

用户提供的日期或筛选值不拼进 SQL 字符串，而使用命名占位符：

```sql
WHERE o.order_purchase_timestamp >= :start_date
  AND o.order_purchase_timestamp < :end_date_exclusive
```

参数另行传入：

```json
{"start_date":"2018-06-01","end_date_exclusive":"2018-07-01"}
```

这样可以把 SQL 结构和值分开。Day 7 由分析计划确定参数合同，SQL 生成响应必须逐项匹配；缺少、多出或改写参数均不执行。

### 三种“正确”不能混用

| 层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 语法正确 | 数据库能解析语句结构 | 表字段存在、查询能执行 |
| 可执行 | 数据库接受查询并返回结果 | 指标、时间、分母和粒度正确 |
| 结果正确 | 与指标口径和独立参考结果一致 | 对其他问题也一定正确 |

本次 `D7_03` 是实跑反例：`COUNT(DISTINCT customer_id)` 语法正确且可执行，返回 96,478；指标要求按 `customer_unique_id` 识别真实客户，参考结果为 93,358，因此归为业务口径错误。

数据库游标结果通过 `rows_to_dicts` 读取 `cursor.description` 中的列名，再将每行转换为字典，统一得到 `list[dict]` 形式，便于 JSON 保存、接口返回和参考结果比较。

## 2. 实现闭环

```text
公开/合成问题
→ KeywordRetriever v1 分别召回指标 Top-5、Schema Top-8
→ 将完整检索候选注入 Day 5 AnalysisPlanner
→ Pydantic + MetricCatalog 结构/跨字段/指标语义校验
→ 检查计划指标确实在本次召回中
→ 从唯一指标字典补全公式、时间、维度、粒度和限制
→ 从维度/数据库字典及 DDL 补全所需表字段和 JOIN 上下文
→ SQL JSON 生成与命名参数合同校验
→ 单 SELECT/WITH 基础检查
→ SQLite URI `mode=ro` + `PRAGMA query_only=ON` 执行
→ 游标行转换为字典列表
→ 独立参考查询核对结果并分类错误
```

规划 Prompt 不再只包含指标和维度 ID；它同时包含本次检索文档的定义、公式、字段、默认时间、允许维度、粒度和限制。SQL Prompt 使用计划级上下文，仅补充已验证计划所需的规范定义和表结构，并明确记录补充来源。

完整离线记录保存问题、两类召回结果、分析计划、SQL 上下文、SQL、参数、查询结果、错误、模型请求消息、模型配置、响应来源、调用次数、运行时间及数据库路径。完整记录在 `data/processed/day07/offline_benchmark.json`，属于可再生成产物；精简结果保存在 `docs/DAY07_BENCHMARK_RESULTS.json`。

## 5. 检索与规划 grounding 修正

学习过程中用户指出：如果规划应依据检索，为什么未召回的合法指标仍能被规划模型输出。检查确认 Day 5 遗留 Prompt 同时暴露全部 27 个指标 ID 和本次召回候选，且假客户端并不会真实依据 Prompt 推理。现已修正：

- 有检索上下文时，规划 Prompt 只把本次召回的指标作为可选候选，不再把全部目录 ID 暴露为另一组选项；
- `ready` 输出必须携带 `evidence_document_ids`，每个所选指标必须引用对应的 `metric:<metric_id>` 文档；
- 程序检查所有证据均来自本次召回，否则在 SQL 生成前停止；
- 运行时记为 `plan_grounding`，因为仅凭一次在线请求无法区分检索漏召回与规划忽略上下文；
- 只有带参考标签的离线评测确认规范指标未进候选时，才进一步归因为 `retrieval`。

完整指标目录继续作为程序侧唯一语义来源，用于未知指标、未知维度和指标维度兼容性校验，不再作为模型可绕过检索自由选择的候选列表。

## 6. 已授权真实 API 批次

用户在了解问题范围、上下文、模型和限次后明确授权真实 API。实际发送 4 个公开问题：`D7_01`、`D7_02`、`D7_04`、`D7_05`。

- 规划上下文：KeywordRetriever v1 的指标 Top-5 与 Schema Top-8，包含返回文档的完整定义和限制；
- SQL 上下文：验证后的 AnalysisPlan、匹配指标的规范定义、所需表的字段/DDL、选中维度映射和参数合同；
- 不发送：数据库业务行、`data/raw/` 内容、API Key、公司数据；
- 模型：`deepseek-v4-flash`，temperature 0，thinking disabled，JSON response format；规划 `max_tokens=1024`，SQL `max_tokens=2048`，单次超时 30 秒；
- 限次：每题 1 次规划 + 1 次 SQL 生成，不启用 SQL 自动修复或输出纠正，共最多 8 次逻辑模型调用；对暂时性网络错误最多 2 次 HTTP 尝试，批次 HTTP 请求上限为 16；
- 执行：每条生成 SQL 仍经过 Day 7 基础检查和只读执行，失败即记录并停止该题，不进入 Day 9 修复循环。

第一次在受限本地环境运行时产生 8 次本地网络失败，没有供应商响应、Token 或可报告的模型延迟。随后按授权使用允许外部连接的执行环境运行：

- 4 题均得到合法、有召回证据的 AnalysisPlan；
- 4 题均生成参数化 SQL 并通过只读执行；
- 4/4 查询结果与独立参考查询一致；
- 每题实际 1 次规划、1 次 SQL 生成，共 8 次成功响应，没有网络重试或 SQL 修复；
- 请求模型配置为 `deepseek-v4-flash`，供应商响应报告模型名为 `deepseek-flash`；
- 供应商返回总用量为 28,152 输入 Token、739 输出 Token；未计算或虚构费用；
- 完整公开 Prompt、响应、中间状态和结果保存在 `data/processed/day07/live_batch.json`，精简结果保存在 `docs/DAY07_LIVE_RESULTS.json`，未发现密钥标记。

这是四题真实冒烟结果，不是完整模型准确率，也不是独立留出评测。
