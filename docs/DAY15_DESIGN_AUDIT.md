## 2. 三个待评版本的严格定义

### V1：直接 SQL（`direct_sql`）

只接收 `cases.public.jsonl` 的公开题面，以及所有版本共同使用的最小公开数据库
Schema 和候选输出合同。一次模型生成必须直接选择：给出 SQL 与命名参数、请求澄清、
拒绝，或报告无法回答。它不调用业务资料检索、不运行分析规划器、不进入 Day 11
状态机、不自动修复，也不执行 Day 10 确定性计算。

### V2：检索 + SQL（`retrieval_sql`）

接收与 V1 相同的公开题面、Schema 和输出合同，唯一核心增量是使用现有 Day 6
检索器取得指标字典、维度字典和数据库字段的公开业务上下文，再进行一次候选生成。
它不使用分析规划器、状态机、候选系统内安全门、自动修复或确定性计算。因此
V2−V1 主要估计“现有检索上下文”在该生成设置下的关联影响，不等于普遍的 RAG
因果效果。

### V3：完整 Agent（`full_agent`）

复用现有 Day 11 工作流：检索、结构化规划、SQL 生成、Day 8 安全门、只读执行、
Day 9 有限修复、Day 10 确定性计算、展示与终止状态。保留同一 `run_id` lineage、
节点合同、16 步上限、修复资格和停止原因。Day 15 不复制 Day 12 的状态到 HTTP
映射，也不以 Day 13 页面状态作为正确性证据。

## 3. 共享组件与真正差异

三版本共享同一公开题面顺序、冻结数据库、结果封存格式、外部只读评测沙箱、私有
评分器、评分规则和机器环境。对等的生成调用共享模型标识、温度、随机种子或其他
采样参数、单次超时和最大输出 token。

上下文长度不强制相同：检索上下文本来就是 V2/V3 的处理差异，因此应记录实际输入
token，而不是截断成看似相同的 token 数。调用次数也不强制相同：多阶段调用与修复
成本是 V3 的真实代价，必须逐次记录。

外部评测沙箱是防止 V1/V2 危险 SQL 触碰数据库的共同实验保护，不是候选能力。
原始记录必须同时保存“候选自己的安全动作”和“沙箱最终安全决定”；沙箱拦截不能
计为 V1/V2 自主安全正确。

## 4. 主实验、开发、冒烟、消融与回放

- `smoke`：只验证 I/O、封存、恢复和计量链路；不报告准确率。
- `development`：只能使用 Day 6/7 或新建的非最终集样本；可调 Prompt，但记录轮次、
  依据和暴露范围。
- `main_experiment`：冻结配置后首次运行 60 题；接触最终集结果后不得逐题修改再继续
  称为盲测。
- `ablation`：预先登记的组件移除或替换；使用同一题目和评分规则，结果明确标为消融。
- `deterministic_replay`：用已封存候选重跑执行或评分，验证可复现性；不是新模型样本。

假模型、确定性回放与真实模型使用互斥 provenance。当前没有真实模型调用授权，
因此真实模型主实验保持未运行。

## 5. 隔离、封存与防污染

候选阶段只可读取公开清单和明确登记的公共运行资产，不可读取数据集 JSON、参考 SQL、
参考结果、比较规则、私有备注或 Day 14 评分输出。每个版本先完成全部 60 题候选输出，
写入不可变 JSONL，计算 SHA-256 并生成运行清单；只有封存成功后，评分进程才加载私有
金标准。候选适配器不得导入 Day 14 私有 Schema/评测器模块或访问 references 目录。

若发现冻结金标准疑似错误，只登记勘误建议；v1.0.0 主实验仍按原合同评分。只有用户
明确批准新版本后，才能重新冻结并重跑所有版本。

## 6. 随机性、重复与样本不确定性

真实模型运行时优先使用提供商支持的固定 seed，并固定 temperature、top-p、最大输出、
工具配置及模型快照；不支持 seed 时明确记录。温度 0 也不保证完全确定。

最低主实验可采用每版本一次完整运行，但这只能估计该次配置在 60 个固定题上的表现，
不能估计生成随机性。若获得真实调用授权且预算允许，预先选择每版本相同的重复次数，
按 case 配对保存每次样本；不得只重跑失败题。比例指标给出分子/分母与 Wilson 区间；
版本差异优先使用题目配对 bootstrap 或配对二项方法。分类只有 10 题时区间会很宽，
报告应强调描述性证据而非普遍优越性。

## 7. 输出错误、超时、限流与环境失败

非 JSON、合同校验失败、空输出、模型超时、限流、传输错误和本地环境失败使用不同
失败类别。传输重试只增加模型传输 attempt，不增加 SQL attempt；生成新 SQL 才增加
SQL attempt。Day 8 安全拒绝、资源超时和环境失败不进入修复。缺失 token 或费用必须
记为 `null`/不可用；离线假模型的外部调用、token 和费用为 0，不能估算成真实用量。

## 8. 多层评分与聚合

逐题分别记录候选输出、SQL 生成、候选安全动作、沙箱安全决定、SQLite 进入行为、SQL
执行、结果等价、工作流状态、stop reason、calculation status、是否发生不允许修复、
四类 attempt、业务参考状态、业务正确性、延迟、调用数、token、费用和最终失败类别。

每个比例独立报告分子与适用分母。没有独立业务金标准的题标为
`not_independently_evaluated`，不进入业务正确率分母。HTTP 成功、状态机成功、SQL
执行成功、结果正确、确定性计算完成、安全正确和业务正确不得汇总成单一成功率。

## 9. 失败归因与混杂因素

失败分类先按最早可归因边界记录：输出合同、检索、规划、SQL 生成、候选安全选择、
安全门、数据库执行、修复控制、确定性计算、状态映射、结果语义或环境。还应保留后续
连锁失败，不用单标签掩盖多个问题。

V2 与 V1 的差异同时受检索内容、额外上下文长度和 Prompt 版式影响；V3 与 V2 的差异
同时包含规划、安全、修复、计算和多调用预算。除预登记的单组件消融外，不能把整体
差值单独归因于某个组件。至少十个案例应覆盖代表性成功与失败边界，而不是只挑最差
输出。

## 10. 建议的必要消融

在资源允许时，仅做能回答明确问题的最小消融：V2 对 V1 估计现有检索包的关联影响；
V3 关闭有限修复观察修复路径贡献与成本；V3 保留状态机但关闭确定性计算，观察计算
边界；安全门不得为追求分数而关闭并执行危险 SQL，可用“仅记录门决定、不执行”的
安全消融。所有消融都复用封存与评分流程，不能修改冻结规则。

## 11. 延迟、调用、token 与费用

记录每题端到端 wall-clock、每阶段耗时、模型调用数、每次传输 attempt、输入/输出
token、缓存 token（若提供）、计费货币、单价来源和费用。汇总报告中位数、均值、
p95、总调用、总 token 和总费用，并区分成功与失败路径。提供商不返回用量时保持
不可用，不按字符串长度伪造 token；单价未知时只报告 token，不猜费用。

## 12. 当前实验不能支持的结论

60 道助手机械题、单个公开数据集、零独立业务参考与单一模型配置，不能证明生产泛化、
跨数据库泛化、统计显著的模型优越性、真实用户体验、业务因果解释或投资回报。离线
假模型可验证工程合同，不能代表真实模型准确率。Docker 可验证打包、启动、健康检查、
只读数据挂载和离线复现，不证明生产安全、扩缩容、高可用或云部署能力。

## 13. Docker/Compose 与依赖边界

Docker/Compose 后续只验证固定 Python 环境、API/UI 启动、健康检查、只读 SQLite/原始
数据边界及离线评测命令。密钥只允许运行时环境变量注入，不写入镜像或 Compose 文件。
模块 1 不新增依赖；现有标准库、Pydantic、pytest、SQLGlot 和项目组件足以定义协议。
若后续需要统计区间，优先用标准库实现；新增依赖必须使用窄版本范围并说明必要性。

## 14. 可重复运行清单的最低字段

每次运行必须记录 run ID、运行目的、结果 provenance、三个版本之一、数据集版本及三类
哈希、数据库哈希、Git commit、工作区状态、Python 与依赖版本、操作系统、模型/提供商、
Prompt/检索/配置哈希、温度与随机性、开始结束时间、公开输入数、封存输出路径与哈希、
外部调用/token/费用可用性，以及评分是否在封存后才加载私有参考。

## 15. 模块 1 实现结论

`src/ecommerce_agent/day15_protocol.py` 以不可变定义固定三版本能力矩阵、四个冻结输入
哈希、运行目的、结果 provenance、共享公平控制和多层测量字段。该模块无模型客户端、
无 Prompt、无金标准读取和无副作用。对应测试防止后续适配器把检索基线悄然升级为
完整 Agent，或把外部沙箱保护误计为候选安全能力。
