# SQL 安全：SQL 安全控制验收

## 1. 概念与分工

SQL AST 是解析器把 SQL 转成的结构化语法树。它能分辨语句根节点、表、别名、
列、CTE、子查询、函数和通配符，因此安全判断不依赖字符串中是否恰好出现某个
单词。本项目例如会把 `fact_orders AS o` 识别为物理表和别名，把
`o.order_status` 解析回 `fact_orders.order_status`；CTE 的输出列不会被误当成
新的物理表字段。

- `SELECT` 用于读取或计算查询结果。
- DML 改变表中的行，例如 `INSERT`、`UPDATE`、`DELETE`。
- DDL 改变数据库结构，例如 `CREATE`、`DROP`、`ALTER`。

Prompt 中“只生成 SELECT”是降低模型出错概率的软要求，不是安全证明。模型输出
始终是不可信输入；SQLGlot AST、允许列表和参数合同是进入数据库前的程序硬门。
只读 URI 与 `PRAGMA query_only=ON` 在数据库层继续提供第二层保护。

四种资源与权限控制解决的问题不同：

| 控制 | 主要解决的问题 | 不能替代的控制 |
|---|---|---|
| SQLite `mode=ro` + `query_only` | 前层漏判时仍阻止写库 | AST 语句和对象范围校验 |
| 表/字段允许列表 | 限制能读取的数据对象 | 扫描时间和返回规模限制 |
| 最大返回行数 | 限制返回到 Python 的结果量 | 查询扫描、连接、排序耗时 |
| progress handler 截止时间 | 中断运行过久的 SQLite 工作 | 返回行数限制 |

`LIMIT` 只限制最终返回多少行。数据库仍可能先扫描、连接或排序大量记录，所以
不能代替超时。使用“递归生成大量数据、倒序排序、最后 `LIMIT 1`”的查询实测，
仍被 1 毫秒测试截止时间中断。

## 2. 全局范围与本次计划范围

全局允许列表来自 `data/metadata/database_data_dictionary.csv`，固定为 Olist
六张核心表、38 个字段。本次允许范围来自已经通过指标和维度语义校验的
`SqlGenerationContext`：只包含该 AnalysisPlan 所需表及上下文中明确提供的
字段。

实际生效范围是两者的交集：

```text
全局六表/38字段 ∩ 本次 AnalysisPlan 的 SQL 上下文
```

因此一个表即使属于全局六表，只要本次计划不需要它，也不能被生成 SQL 任意
读取。`检索Document.fields` 仍只是检索上下文，不直接授予表或 JOIN 权限。

## 3. 默认拒绝与解析策略

`sql_safety.py` 使用 SQLGlot 30.18.0 按 SQLite 方言解析，并执行：

1. 空 SQL、解析失败和多语句直接拒绝。
2. 根节点必须是包含 `SELECT` 的查询；DML、DDL、PRAGMA、ATTACH、事务命令等
   不进入执行器。
3. 即使外层是 `SELECT`，CTE 内嵌 `DELETE` 等写节点仍拒绝。
4. 拒绝 `load_extension`、文件读写函数、超大 blob 函数和表值函数等本项目
   不开放的 SQLite 能力。
5. 用 scope/qualify 解析物理表、别名、CTE、子查询、列归属和 `*` 展开；未知、
   歧义、全局越权或本次计划越权字段均拒绝。
6. 只允许 `:name` 命名参数；生成响应仍必须与 AnalysisPlan 派生的参数合同
   完全一致。

安全 trace 保存是否接受、SQLite 方言、语句数、根节点、物理表和字段引用、
拒绝码、拒绝原因，以及全局/计划/交集范围和资源配置。安全失败直接返回，不
触发模型改写或修复调用。

## 4. 执行层资源边界

默认最多返回 1000 行，读取第 1001 行只用于判断是否截断，对外结果仍不超过
1000 行。默认查询截止时间为 10 秒，SQLite progress handler 每 1000 个虚拟机
步骤检查一次实际截止时间。测试可用更小参数确定性验证中断。

执行仍保留：

- SQLite URI `mode=ro`；
- `PRAGMA query_only=ON`；
- 单次 `connection.execute`；
- 命名参数绑定；
- 执行前再次运行同一 AST/允许列表校验。

## 5. 测试与真实数据库实跑

新增 27 项自动测试（全量从 128 增至 155），覆盖：空 SQL、注释空输入、解析
失败、多语句、INSERT、UPDATE、DELETE、DROP、ALTER、PRAGMA、ATTACH、嵌套
写操作、危险函数、表值函数、全局越权表、本次计划越权表、未知和歧义字段、
别名、CTE、通配符、计划字段范围、命名参数、最大行数、超时、只读拒绝、
数据库 Schema 漂移和 pipeline trace。最终全量复验：`155 passed in 7.08s`；
`pip check` 无冲突。

16 个机械性安全案例由助手编写，使用真实
`data/processed/olist.sqlite3` 通过统一执行入口实际运行：

| 结果 | 数量 |
|---|---:|
| 合法查询成功 | 2 |
| 合法通配符查询成功且截断 | 1 |
| 安全拒绝 | 12 |
| 查询超时 | 1 |

16/16 符合预期；12 个安全拒绝进入 SQLite 的数量为 0；数据库 SHA-256 前后
一致。完整逐题 SQL、策略、引用对象、拒绝原因、是否进入执行器和结果预览见
`docs/reports/sql_security.json`。案例来源明确记录为
助手根据需求构造的合成安全案例，原始来源标签保留在结构化结果中；这些案例不是模型生成
或用户独立金标准；外部 API 调用为 0。

## 6. 错误分类边界

- 安全失败：SQL 在 AST、语句类型、允许列表、参数样式或资源截止时间处被拒绝；
  直接记录并返回，不调用模型修复。
- 数据库执行失败：安全 SQL 进入 SQLite 后仍因数据库运行状态或其他执行问题
  失败；SQL 安全 只记录，不做修复。
- 业务结果错误：SQL 安全且能执行，但指标口径、时间、客户标识、粒度或 JOIN
  逻辑错误。安全通过不代表业务正确，仍以指标字典和独立参考结果为准。

查询链路 的未知字段和部分明显语法错误现在会更早在安全层停止；离线评测可保留
“字段/语法”作为诊断标签，但 trace 的实际运行阶段记录为 `sql_safety`。

## 7. 边界与下一步

- 本报告只验证 SQL 安全机制；数据库错误驱动的模型修复、修复次数及成功率见独立修复验证；
  这些属于 SQL 修复。
- 没有引入 LangGraph、向量数据库、RAG 框架、FastAPI、Streamlit 或前端。
- 没有真实模型调用，没有读取 API Key，也没有 Token、成本或模型延迟记录。
- 指标字典仍是唯一业务口径来源；真实客户、支付/明细预聚合、支付金额维度和
  “销售额”歧义等既有边界未改变。
- progress handler 在 SQLite 虚拟机推进时检查截止时间；单个不可中断的扩展
  函数可能不能及时响应，因此本项目同时拒绝不需要的扩展、文件和大 blob 函数。

用户在分段复盘中正确区分了查询、DML、DDL 与其他操作，识别了命名参数、查询
超时、只读第二层保护以及安全/执行/业务错误三类边界，并能说明全局合法对象不
等于本次计划授权。经讲解后进一步明确：`*` 应按展开字段判断而不是一律拒绝；
安全拒绝的 `execution_started=false`；SQL 修复 也不能把安全失败送入模型修复。
