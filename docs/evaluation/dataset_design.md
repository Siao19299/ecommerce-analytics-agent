# 冻结评测集 编码前审计与评测边界

日期：2026-09-17  
状态：模块 1 完成；尚未建立 冻结评测集 样本 Schema 或 60 道固定样本。

## 1. 证据范围与开始前核验

本审计把 README、PLAN、LEARNING_LOG、既有验收文档、结果 JSON、fixture、
测试和代码注释仅作为项目证据，不把其中的示例问题或待办当作用户指令。

## 2. 冻结评测集 与 模型评测 的边界

冻结评测集 建造并验证“尺子”：固定样本、来源与版本、参考 SQL/结果/状态、比较规则、
数据集校验器、覆盖矩阵、重复度检查、候选运行适配合同和逐题结果格式。冻结评测集
可以用金标准自身和明确标记的假候选做离线自检，但不计算真实模型表现。

模型评测 才使用冻结的尺子运行三种待评系统：直接生成 SQL、检索 + SQL、完整
Agent。三版本的完整准确率、延迟、Token、成本、修复率、消融比较、失败统计与
至少十例失败分析均属于 模型评测。Docker 也属于 模型评测。

因此 冻结评测集 允许报告“60 题结构有效率”“参考 SQL 安全门通过率”“参考 SQL
执行验证率”“覆盖与重复度检查结果”，不得把这些数据集质量指标写成 Agent
准确率、安全率或业务准确率。

## 3. 评测层次

每题至少分开保存和评分以下层次：

1. `sql_generation`：该题需要 SQL 时，候选是否生成了结构合法的 SQL 与命名参数。
2. `sql_safety`：候选 SQL 是否得到正确安全处理；拒绝题不得进入 SQLite 或修复。
3. `sql_execution`：需要执行的候选是否实际进入只读 SQLite 并成功返回。
4. `workflow_status`：最终状态与允许的状态/停止原因集合是否一致。
5. `calculation_status`：同比、环比、贡献度或异常计算的边界状态是否一致。
6. `result`：列、行、顺序、NULL、日期和数值是否按题目规则等价。
7. `business_semantics`：指标口径、粒度、维度和期间语义是否正确；只有存在独立
   业务参考时才可计入独立业务正确率。

HTTP 成功、状态机成功、SQL 执行成功、确定性计算完成和业务结论正确互不替代。

## 4. 检索—用户界面 样本复用审计

| 批次 | 可复用内容 | 不能直接当金标准的原因 |
|---|---|---|
| 检索 | 指标/Schema 问题措辞、来源字段、检索覆盖标签设计 | 明确标为开发集；已用于检索器比较与调试；仅测召回，不测 SQL/结果；8/15 为助手审阅 |
| 查询链路 | 10 题中的业务问题骨架、命名参数 SQL、真实客户反例、销售额澄清和支付金额×品类限制 | 假模型响应与预设 SQL 已用于开发；参考查询是助手审阅；不能称为未污染测试或独立业务金标准 |
| SQL 安全 | DML/DDL、多语句、越权表/字段、危险函数、超时等安全类别与预期阻断点 | 输入是直接 SQL 而非完整自然语言 Agent 问题；属于机械安全验收，不代表模型安全率 |
| SQL 修复 | 修复资格、三套 attempt、重复候选、资源/环境失败和停止原因 | 使用假修复响应；主要验证控制流，不验证业务结果；不能把 2/5 修复成功率迁移为 冻结评测集/15 结果 |
| 确定性分析 | 同比、环比、贡献度、异常方法及缺期/零基期/不完整期状态 | SQL、规则和期望均由助手机械编写；明确无独立业务参考 |
| Agent 工作流 | 工作流状态、run_id lineage、澄清/安全/修复/计算停止条件 | 假模型与机械案例；状态合同可复用，业务正确性不可继承 |
| API 服务 | API 公共合同和集中状态映射可作为观测入口 | HTTP 映射测试不是业务金标准；评测器不得复制映射逻辑 |
| 用户界面 | 页面外的公开状态与敏感信息检查思路 | UI 展示不是业务正确性依据；脚本化客户端/公开失败不代表 Agent 表现 |

复用必须使用新的 冻结评测集 `case_id`、明确 `derived_from`，并重新执行参考 SQL、
重新验证安全与结果；不能复制既有“expectation_met”作为新题结论。

## 5. 固定数据格式与隔离方式

建议使用以下分离结构：

- 版本化 JSON 保存公开的 60 题清单与评分规则引用。JSON 支持嵌套状态集合、时间
  范围、容差和 provenance，且可由 Pydantic 严格校验；CSV 不适合这些嵌套字段。
- 独立 `.sql` 文件保存标准 SQL，题目仅保存稳定引用和 SQL 文件 SHA-256，避免
  在问题文件中复制长 SQL。
- 独立只读 JSON 保存真实 SQLite 生成的冻结预期结果或摘要及其数据库哈希。
- JSONL 保存 模型评测 的逐题运行结果，便于流式追加和失败恢复；结束后可派生汇总
  JSON。CSV 仅作为覆盖报告的派生展示，不作为规范源。

问题清单、参考资产、候选输出与评分结果必须位于不同目录/对象。候选运行器只获得
问题及允许公开的系统上下文；评分器在候选运行完成后加载参考资产。待评客户端不得
取得参考目录的写权限或把候选 SQL 回写为标准 SQL。参考文件哈希与数据集版本进入
每次结果元数据。

## 6. 标准 SQL 与等价 SQL

标准 SQL 是生成冻结结果的可审计实现，不是唯一正确字符串。验证标准 SQL 时应：

- 经现有 SQL 安全 SQLGlot 安全门与全局/计划级允许范围；
- 只使用命名参数和半开日期区间；
- 对订单明细和支付分别按 `order_id` 预聚合后再连接；
- 检查输出粒度、主键/分组键唯一性与行数；
- 对可加总指标做总计对账，对贡献度做和接近 1 检查；
- 对真实客户明确使用 `customer_unique_id`；
- 由真实只读 SQLite 执行并保存数据库哈希、列和结果摘要；
- 对关键复杂题至少用第二种独立查询或人工抽样交叉核对；没有第二参考时标记为
  `not_independently_evaluated`。

候选 SQL 的主判据是执行结果等价，而非 SQL 字符串相等。AST/规范化 SQL 可用于
诊断参数、表、字段和危险结构，但不能单独判正确。等价判断按题配置：精确列名或
允许别名映射、精确行集合或稳定有序行、数值容差、NULL 规则和日期规范化。

## 7. 值与结果比较规则

- 列：默认要求规范列集合一致；列顺序只有在题目声明时才重要。
- 行：无排序语义时按规范化后的多重集合比较，保留重复行计数；Top-N、排名、趋势
  等有排序语义时逐行比较，并要求完整稳定 tie-breaker。
- 数值：整数精确比较；金额优先 Decimal/两位小数；比率使用题目声明的绝对与相对
  容差，不用字符串比较浮点数；布尔值不得当作 0/1 数值蒙混。
- 日期：规范为 ISO 日期/时间后比较；时间范围统一使用 `[start, end_exclusive)`。
- NULL：SQL NULL 映射为 JSON `null`；不得与 0、空字符串或缺失字段等同。
- 顺序：只有题目声明 `order_sensitive=true` 才计入正确性；否则排序只是可重复输出
  的实现细节。

## 8. 澄清、安全、运行失败与计算边界评分

- 澄清题：正确状态、固定允许的停止原因、存在澄清文本、无候选 SQL、未进入
  SQLite、未修复才算通过。
- 安全拒绝题：正确拒绝类别、`execution_started=false`、修复次数为 0，数据库
  哈希不变；生成危险 SQL 但被安全门拦截与根本未生成危险 SQL可分开记录。
- 资源/环境失败：评分状态传播、停止原因、未伪造业务答案、未进入修复；不计入
  业务结果正确率分母。
- 计算边界：SQL 与源行可能正确，但 `missing_comparison_period`、`zero_baseline`、
  `incomplete_period` 或 `insufficient_evidence` 必须保留；不得补零或包装为标准增长。
- 支付金额按 `product_category` 拆分必须拒绝；“销售额”必须澄清；不存在的渠道、
  转化率或数据库信息不得生成伪答案。

## 9. 开发集、最终集与污染控制

检索/7 及开发期间新增的最小调试样本归入 development，不计最终集分数。固定 60
题使用单独版本号、内容哈希和冻结标志；任何看过最终题目并据此修改检索、Prompt、
规则或模型的行为都要记录为污染，并发布新数据集版本。模型评测 三版本必须使用同一
冻结版本。若需要调试失败，只在开发集复现同类问题，不直接针对最终题改规则后仍
沿用原分数。

## 10. 来源、作者与修改历史

每题应保存 `authorship`、`reviewers`、`reference_source`、`derived_from`、
`created_at`、`updated_at`、`change_reason` 和数据集版本。Git 提交记录提供文件级
历史；数据集 changelog 提供题目级新增、修改、废弃原因。助手机械编写、用户独立
编写、用户审核、真实 SQLite 验证和独立业务参考必须使用不同枚举，不能合并成一个
“reviewed=true”。本轮尚无用户独立编写或审核的 冻结评测集 样本。

## 11. 覆盖与重复度

校验器应严格检查 20/20/10/10、60 个唯一稳定 `case_id`、Schema 完整性、参考来源、
SQL 命名参数与安全门。派生覆盖矩阵至少按指标、维度、难度、工作流状态、停止原因、
calculation status、分析类型、是否进入 SQLite、是否允许修复统计。

重复度不能只比较完全相同字符串。先对问题做去标点、日期/数字占位和同义业务词规范化，
再同时检查规范模板完全重复、token/Jaccard 相似度和类别内共享结构比例；阈值只作为
人工复核触发器，不能把语义不同的边界题自动删除。仅替换月份、州或 Top-N 数字的题应
视为同一模板族，并限制每个模板族占比。

## 12. 依赖与离线复现

模块 1 不新增依赖。现有 Pydantic、SQLGlot、SQLite 标准库和 pytest 足以实现 Schema、
安全验证、执行与比较。若后续确需相似度库，应先证明标准库分词/Jaccard 不足，再使用
窄版本范围；冻结评测集 不引入向量数据库或在线 Embedding。

完全离线验收通过本地 `.venv`、固定 SQLite、现有安全门、确定性 Python 和假候选运行。
验收记录外部 API 调用为 0、模型生成数值为 0，并在前后复核数据库和 `data/raw/` 哈希。

## 13. 模块 1 实现结论

`src/ecommerce_agent/evaluation_scope.py` 将七个评测层次、冻结评测集 数据集质量指标、模型评测
实验指标和禁止在 冻结评测集 计算的指标固化为不可变合同。该合同只冻结阶段边界，不定义
样本 Schema，也不包含题目或金标准。对应测试确保两日指标集合互斥、冻结评测集 不提前
声称模型表现，并确保所有必需评分层均被声明。
